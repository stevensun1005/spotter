# 训练搭子 Spotter 软件设计

本文记录用户实际操作、客户端和服务端实现，以及功能改动时需要一起维护的资料。功能状态以本文链接的源码和实际验证为准。生产、测试和私密试用的发布记录另行核对。

## 产品与运行环境

Spotter 围绕「安排训练 → 逐组记录 → 完成打卡 → 回顾和分享」组织功能。饮食、身体记录和设备数据都是本人账号的独立记录。用户可以自行训练，也可以邀请搭子、连接普通好友，或与教练建立独立关系。

| 环境 | 客户端与后端 | 身份和数据边界 |
| --- | --- | --- |
| iPhone App | [SwiftUI 源码](../ios/SpotterHealth/) → 原生 `NativeAPI` → Cloudflare HTTPS API | 默认和 Cloudflare 网页使用同一账号与 D1。登录后才进入主界面，已验证的账号可离线访问在本机缓存的训练。 |
| Apple Watch | [watchOS 配套 App](../ios/SpotterWatch/) → HealthKit、Workout Mirroring、WatchConnectivity → iPhone | 训练期间使用 iPhone 当前草稿，训练结束由 iPhone 打卡。健康数据按账号和训练关联。 |

| Cloudflare 网页 | [网页与 API](../cloudflare/app/) → [业务模块](../cloudflare/features/) → Workers + D1 | 产品网页和 App 的云端数据入口。TestFlight 的部分好友和头像请求可走独立 Beta Worker，使用同一个 D1 和账号会话。 |

| 独立 Node 自托管版 | [Next.js 页面/API](../app/) → [功能](../features/) → [服务端](../server/) → SQLite | 独立账号、设备令牌及数据库，支持计划、逐组训练、搭子和设备导入。 |

## 登录与初次使用

1. iPhone 使用「通过 Apple 登录」或 Google 登录。已有账号可用访问码。登录后从「今日 → 设置 → 账号」编辑头像、昵称和 `用户名#编号`，或绑定另一种登录方式。绑定动作在已登录的账号下完成。之后分别用 Apple 或 Google 登录，服务端按各自身份找到同一个 Spotter 账号。
2. 昵称是联系人、朋友圈和搭子界面的主要显示名称。用户名和数字编号可编辑，完整组合必须唯一，用于查找好友或搭子。个人账号页管理登录绑定、隐私及删除账号。
3. 初次进入支持当前引导版本的客户端会看到欢迎页。可以按需「授权 Apple 健康」「允许 iPhone 通知」，随后选择「开始使用引导」或「跳过引导」。引导高亮真实训练、饮食、社交和 AI 入口，最后带用户从教练菜单走到「用自己的 AI」的使用教学。试填训练或餐食及试搜搭子时，保存或发送按钮会限制写入。可以跳过一节或结束引导。以后从「设置 → 关于与更新 → 重新查看使用引导」重开，原有账号的完成进度继续有效。
4. 可选权限的提醒按账号和服务地址记录。仍需授权或核对时，两次提醒至少相隔 14 天。系统对相机、照片、麦克风和语音识别的授权在使用相应功能时出现。Apple 健康读不到样本时，界面区分需授权、需核对、已能读取部分数据和用户已确认。

实现见 [NativeApp](../ios/SpotterHealth/NativeApp.swift)、[NativeAccount](../ios/SpotterHealth/NativeAccount.swift)、[NativeWelcome](../ios/SpotterHealth/NativeWelcome.swift)、[NativePermissionOnboarding](../ios/SpotterHealth/NativePermissionOnboarding.swift) 和 [Cloudflare 账号与 OAuth](../cloudflare/features/auth/)。原生 API 会话保存在设备 Keychain。OAuth 配置见 [Apple 和 Google 登录](cloudflare-login.md)。

在「设置 → 账号 → 头像」保存或移除照片后，首页的今日搭子打卡、联系人、朋友圈、账号页及打开的训练分享卡共用同一个头像状态。切换标签、App 回到前台或网络恢复时，会刷新当前显示的头像，前台也会定期补查。已删除的头像回到首字占位。照片只缓存在当前账号的 App 进程内，写入仍由本人通过 `/api/auth/avatar` 完成。读取接口 `/api/auth/avatars` 使用当前会话，只返回本人、可见好友、搭子及有效教练关系的头像。[原生头像状态](../ios/SpotterHealth/NativeAccountAvatar.swift) · [服务端头像可见性](../cloudflare/features/auth/visible-avatars.ts)

## iPhone 导航与核心流程

「今日」「训练」「统计」「好友」由 SwiftUI `TabView` 管理，各自保留导航栈。悬浮底栏用同一个胶囊放页面标签和中间的开练按钮。按下标签即点亮，松手后切页。iOS 26 及以上使用液态玻璃，iOS 16–25 使用毛玻璃材质。页面按底栏高度预留底部安全区。标签字号随 App 和系统的大字号设置适度放大，系统辅助功能大字号下可长按查看，iOS 17 起 VoiceOver 会将其读作标签栏。好友入口可在功能模块隐藏。新手引导直接高亮要点的标签、星星和页内按钮。好友顶部和记餐的食物来源使用 `UISegmentedControl`，把 44 点高度留给控件本身。其他分段使用 SwiftUI Picker。六个及以上的选项或辅助功能大字号使用系统菜单。[原生导航](../ios/SpotterHealth/NativeApp.swift) · [原生分段](../ios/SpotterHealth/NativeControls.swift) · [新手引导](../ios/SpotterHealth/NativeWelcome.swift)

AI 教练是右下方的 48 点圆角方形按钮，外圈是四种强调色组成的渐变环。主页面、App 内详情和弹窗共用同一个场景内的悬浮入口。悬浮层只响应星星的触摸，教练面板可打开键盘，关闭后将焦点交回原来的页面。系统授权和键盘保留系统层级。欢迎页和使用引导期间沿用引导按钮。底栏「训练」与「统计」之间的绿色播放按钮打开开练面板，进行中则直接回到本场训练。底栏上方的状态条也可返回，显示计时、组数及可用心率。页面在底部安全区为快捷入口预留高度。打卡月历和二级详情按剩余高度排版，内容较长时可滚动查看。饮食快捷操作位于饮食详情正文。

首页的训练、饮食与打卡共用一个所选日期。从首页打开饮食明细会沿用该日期，明细改选也会同步回来。Widget 入口按 Widget 的日期打开。首页顶部每个日期的深绿色外环显示当天已完成计划的比例，无计划的本人训练也能闭环。浅蓝色内环显示摄入热量占当日目标的比例。饮食明细的日期环、每日热量大环和全彩模式的饮食小组件也用浅蓝色。VoiceOver 可读出每个日期及两种进度。饮食环按账号复用 `/api/data?scope=nutrition&from=…&to=…` 周查询和已有营养目标，单日仍由 `/api/library` 提供明细。训练与打卡沿用日程索引和历史加载。

### 训练、计划与详情

- 训练计时根据起止时间和已累计时长计算，切到后台或锁屏仍继续。可逐组记重量、次数、时长、左右侧及适用的 RPE。计时区下方的休息条可调整或跳过，左侧回转箭头撤销最近完成组，云朵状态在训练类型旁。底栏「更多 → 训练心得」保留随训练保存的笔记。
- 两种训练界面都可为按秒的未完成组点「开始计时」。每场训练可开一个动作倒计时，跟随训练时钟暂停或恢复，最小化和重启后从本机草稿恢复。计时归零等待手动完成。提前完成按实际已用时间记，撤销后恢复原目标秒数。
- 「设置 → 训练偏好 → 训练界面」可选默认「经典列表」或「专注训练」，选择保存在这台 iPhone。专注训练的紧凑顶栏显示训练标题、计时和总体进度。内容突出当前动作、组次和大号重量与次数/时长输入，保留动作演示及下一组预览。休息时用渐变圆环显示剩余时间，可增减 15 秒。「完成第 N 组」和「进入下一组」都固定在训练工具栏上方。没有动作组的有氧或跟练继续用原来的记录区。样式和计时不涉及新的账号权限，完成组沿用现有云端格式。[训练界面](../ios/SpotterHealth/NativeWorkouts.swift) · [专注页](../ios/SpotterHealth/NativeFocusedWorkout.swift)
- 超级组按轮次切换动作。例如 A1 第 1 组、A2 第 1 组、A1 第 2 组、A2 第 2 组。保留计划明确指定的分组和换站，旧计划可从动作编号推断同站分组。iPhone 与手表使用同一个组次排序，iPhone 自动展开下一动作，并可在「设置 → 训练偏好」高亮待完成组。[训练排序和休息规则](../ios/SpotterHealth/NativeWorkoutModels.swift)
- 进行中的动作卡片可直接打开演示、历史与统计。三段动作节奏位于组次和重量旁，可在计划或模板的动作编辑区设定。旧四段数据保留，卡片显示前三段。没有指定节奏的适用力量动作会标出建议节奏。既有草稿、打卡和云端计划沿用原数据结构。[训练页](../ios/SpotterHealth/NativeWorkouts.swift) · [计划编辑器](../ios/SpotterHealth/NativePlanBuilder.swift)
- iPhone 训练底栏的「退出」会暂停计时、保存草稿并返回，「最小化」会继续计时。重新打开暂停的训练仍保持暂停。右上角「结束训练」可保存有内容的训练，试练没有可打卡内容时可返回继续记录或删除这次草稿。
- 训练页只保留训练操作。点「退出」后，首页或「我的计划」的训练卡片「…」菜单提供「重新开始」和「删除本次训练」，未打开的训练草稿提供「删除训练草稿」。底栏上方的状态条只用于返回训练。可在列表向左滑暂停中或未打开的训练草稿，再点系统「删除」并确认。重开沿用训练项目并换新草稿 ID，删除只同步该次草稿的移除。当天排定的计划和之前的打卡会保留。[原生训练](../ios/SpotterHealth/NativeWorkouts.swift) · [全局状态条](../ios/SpotterHealth/NativeApp.swift)

### 饮食与身体

- iPhone 饮食明细只提供「饮食」「饮水」「拍照记录」三个记录入口。「饮食」和「开练 → 记录饮食」都先挑选食物，点「完成」后再选早餐、午餐、晚餐或加餐。选择餐次后统一保存，取消会保留食物篮。食物列表复用当前搜索和分类。「搜索」页未输入时按分类浏览共用食物库：左侧为蛋白质、碳水、脂肪、蔬菜、水果、饮品调味、家常菜、外食快餐和零食甜点，上方标签继续细分。卡片显示每 100 g 的热量和碳、蛋、脂。点「+」按第一个常用份量加入，没有份量时按 100 g。点卡片打开份量页，可按克或按份调整，并查看数据来源。输入「鸡胸肉 150g」这类文字时，按名称、别名和英文名搜索并带入克数，只输入「150g」或「150 grams」不会拆出食物名，「100 granola」「100 gâteau」也不会把开头的 g 当成克。搜索排序为：名称完全相同、别名完全相同、名称开头、名称里某个词开头、别名里某个词开头（别名开头也算在这一级）。英文按整词算，中文、日文、韩文每个字各算一个词，所以「tea」不会找到「sirloin steak」，「pie」不会找到「Rice Krispies」，「big mac」能找到麦当劳巨无霸，「饭」能找到米饭。大小写、全半角和重音都可省略，「creme sure」能找到「crème sure」。同级时日常食物排在连锁店和品牌单品前，再按食物库顺序，原有 22 条在前，所以「apple pie」「芝士汉堡」先出通用的苹果派和芝士汉堡，「steak」「peas」也先出牛排和青豆，不会先出「steak sauce」「pea soup」。iPhone 的 `searchRank` 和网页的 `searchFoods` 这五级规则相同。iPhone 另有两级兜底：输入几个词时每个词都能对上的食物，以及一句话里含有完整食物名的情况，例如「我吃了米饭」。兜底时英文必须是完整的词，「licorice」不会找到 rice。第一个分类顶部列出「最近记过」，按上次份量加入。
- 已选食物在底部汇总热量和三项宏量营养。点篮子可调整、移除或「存为固定模版」。选择餐次后，整篮食物统一使用该餐次。只有一条时用 `/api/library` 保存并显示撤销提示，多条时用 `/api/data` 备份导入。每项使用固定的记录 UUID，失败后再点「完成」会跳过已写入的项，不会重复记录。如果失败后改了份量、餐次或移除了某项，重试前先按 ID 删除上次可能已写入、内容已变的记录，再按当前清单保存。
- 「自定义」新建个人食物（`kind: "food"`），按每 100 g 或每份填写，保存时换算成每 100 g，网页和 iPhone 都能搜到。「直接填写本餐」只记这一次，不存进「我的食物」。份量页右上角星标加入「收藏」。「固定模版」与饮食设置里的模版管理读写原有的本机组合。收藏和条码对应关系按账号保存在这台 iPhone，和常用餐一起在退出账号时清除。
- 右上角「快速录入」提供「扫食物条码」「拍营养元素」「从相册识别营养表」，搜索框右侧也有扫码按钮。扫码先查这台 iPhone 记过的条码，再向 Open Food Facts 的公开接口查询，请求只带条码数字。查到的品名和每 100 g 营养会填进扫码食物。包装有单件数量和每份总重量时，换算成每个重量，默认按个数录入。只识别到以克为单位的每份重量时默认按份数录入。数量变化会同步显示本次重量和营养。资料缺少重量时，可以设置每个或每份的重量，也可按克记录。食物与单位按同一食物 ID 保存，同一条码再次打开会沿用已存单位。营养表照片走 `/api/food-photo` 的 `label` 模式。站内识别不可用时，用 iPhone 本机文字识别读取 Calories、Fat / Lipides、Carbohydrate / Glucides、Protein / Protéines 及中文标签。读到「per 100 g」「每 100 克」时按每 100 g 填写，否则按每份填写。没有读到每份克数时，保存按钮会等用户填写「每份重量」。补拍的照片没有每份克数时，保留之前读到或已填写的每份重量，按每 100 g 读的照片也不改每份重量（括号里的克数可能是整包净含量）。草稿里已有的数值和新照片的计法不同时，知道每份重量就换算，不知道就清空这张照片没读到的项，每 100 g 和每份的数值不会混在一起。从自定义食物页去拍营养标签时，取消拍照或照片无法读取都会回到原来的草稿。相机权限说明涵盖拍餐食、扫码和拍营养表。
- 编辑已有记录、从「食物推荐」打开的单项、饮水和体重沿用原来的编辑表单。填食物名和三项宏量营养，重量选填。「热量（千卡）」留空时，随输入按 `4 × 蛋白质克数 + 4 × 碳水克数 + 9 × 脂肪克数` 显示估算，保存时使用该值。填写的热量（包括 0）优先，可用于包装标注值。编辑记录会先显示原热量，清空后可重新估算。饮水按毫升，数据以当前用户当地日期归档。
- 共用食物库 [`cloudflare/shared/food-catalog.json`](../cloudflare/shared/food-catalog.json) 收录 972 条加拿大常见食物，分 9 个大类、39 个小类，iPhone 打包同一份文件，网页的 [食物搜索](../cloudflare/features/nutrition/foods.ts) 也读取它。原有 22 条 USDA 食物保持 ID、名称、数值和排序，已有记录的 `foodId` 不变。数值来源：USDA SR Legacy（SR28）856 条（含原有 22 条），加拿大卫生部《常见食物营养值》（2008）32 条，连锁店和品牌的加拿大官方营养资料 30 条，零售商页面或 Open Food Facts 上的产品营养标签 11 条，第三方网站整理的连锁店数据 43 条（麦当劳、A&W、星巴克和 Pizza Pizza 的部分单品）。网页份量换算为每 100 g 后写入，详情页显示来源名称和网站。KFC、Popeyes、汉堡王、Wendy's、Domino's、Pizza Hut 和 Little Caesars 只有 SR28 收录的美国门店数据，这些行也标了 `brand`，搜索时和其他连锁店单品一样排在日常食物后面。Tim Hortons 的加拿大官方营养资料这次未能读取，暂未收录，可用通用的甜甜圈、松饼、贝果和咖啡代替。每条记录用 `src` 和 `ref` 标明来源。「食物推荐」和「智能食谱」仍只在原有 22 条里挑选。网页记餐的搜索和「查看全部」使用整份食物库，选中食物后若本人没有保存过份量，就列出食物库自带的常用份量，来源链接文字改为「数据来源」。
- 饮食设置的「管理固定模版」可从当天已记的食物组成组合，记餐页的「存为固定模版」会把已选清单整份存为组合，项数不限，只检查总重量和营养数值是否在记录范围内。App 本机保存组合；使用组合生成的餐食记录写入云端。饮食详情的「拍照记录」直接打开相机，识别结果支持查看、补充、编辑与撤销。可读的标签和用户明确的份量优先，常用「一碗」「一杯」可按可解释的份量估算，并保留估算信息。
- 保存的组合与编辑中的动作行使用 SwiftUI 的原生列表左滑。训练草稿在原有滚动页由 [UIKit 单行列表](../ios/SpotterHealth/NativeDraftSwipeRow.swift) 提供系统左滑。三处滑到底都只展开删除按钮。训练草稿及组合另需确认，组合删除会保留已记餐食。移除编辑中的动作会修改当前编辑草稿，保存后才更新原计划。可用 iOS 16 及以上。
- 「设置 → 蛋白粉仓库」保存产品、一勺粉量、冲泡材料和杯量，可拍照读标签、核对后保存为训练默认。完训选择已喝蛋白粉时，随打卡写逐笔餐食记录。已有记录与重复请求仍按稳定 ID 防重。
- 「设置 → 账号 → 身体档案」或开始训练面板的「身体数据」查看体重、身体测量和身体档案。相关 Apple 健康样本可在本机核对，再同步选定值。身体目标、档案和饮食记录维持各自数据类型。
- iPhone「饮食详情 → 饮食设置 → 营养目标 → 按身体数据计算」与网页「营养目标 → 按身体数据计算」按身体档案和活动估算每日热量及三大营养素。iPhone 使用独立计算页，点目标、活动量或进度进入带选中标记的原生列表。网页在编辑表单上方展开，使用原生选择控件。iPhone 用浅蓝热量卡，网页用深绿热量卡，沿用各自的饮食配色高亮三大营养素。计算依据和校准条件按需展开。两端读取身体档案的身高、年龄、性别和最新体重，以及 90 天内、3%–60% 之间的最近一次体脂。用户选择「目标方向」（维持体重、减脂增肌、增肌增重、减脂）、「日常活动（不含训练）」、「每周训练」和「进度」（仅增重和减脂）。「每周训练」没有保存过时，按近 4 周完成训练的天数预填；预填的天数在本人选了日常活动、改了天数或点了填入之后才随偏好保存。结果显示每日热量、蛋白质、碳水和脂肪，并说明基础代谢、维持热量、每天增减多少和预计每周体重变化。设了目标体重时显示到达时间：12 周以内写「最快约 N 周」，更久写「至少要 N 周，体重变化后请重新计算」，因为维持热量会随体重下降；减脂的目标体重不高于 BMI 18.5 时不估算到达时间。目标体重目前只能在网页设定，iPhone 沿用已保存的值。iPhone 的「填入营养目标」和网页的「填入目标」把数值带回可编辑的目标表单。编辑表单常驻各项目名称和单位。点「保存」后写入账号，直接关闭 iPhone 计算页会放弃该页的更改。所选方向、活动、每周训练和进度随 `targets.preference` 保存。只选了目标方向和日常活动之一时，两端保存都会提示填完整；两项都清空则移除偏好。新增的 `trainingDays`（0–7）和 `pace`（`slow`、`standard`、`fast`）是可选字段，旧数据不用迁移。尚未部署这次改动的 Cloudflare 版本保存时会丢掉这两个字段，偏好下次读出来又被当成旧口径，所以要先部署 Cloudflare，再发带估算器的 iPhone 版本。旧估算器保存的活动量把运动也算在内，口径不同：没有 `trainingDays` 的偏好视为旧口径，估算器里「日常活动」留空并提示重新选择。目标方向、每周训练和进度都没动过时，保存原样保留旧偏好；动过其中任何一项，保存前要先选日常活动。iPhone 从 AI 教练回执打开的饮食详情也带上训练记录，「每周训练」的预填和从饮食页进入时一致。
- iPhone 的计算页在「日常活动」提供手动输入、Apple 健康、训练日历和自动动态估算。Apple 健康取过去 28 个完整的当地日期，在至少 14 天有步数时，按有效天平均值在手动活动档的系数间平滑估算。较小的步数变化不会因跨过手动分档而突然改变目标。使用 HealthKit 合并来自手表和手机的步数，并从每日报告中尽量扣除已记录的训练时段步数。只使用已经记录的 HealthKit 训练估算过去频率。训练计划的变化影响未来训练量，体脂公式中的训练频率仍取近期实际训练。训练日历取今天起 7 天的本人计划，使用计划时长，缺少时长的一堂按 60 分钟。同一天多堂计入各自时长，训练天数只计一次。日历模式可填写平时活动量，自动模式组合近 28 天的健康步数和未来 7 天的日历训练。两项输入缺失时提示补齐或选其他来源，未加载的日历不当作休息周。按打开计算页时取得的数据刷新建议，日期和日历变化会重新估算。建议以未来一周的日均摄入展示，点「填入营养目标」再保存才改每日目标。使用日历的两种模式按前瞻计划估算，原有近四周体重和饮食校准继续用于手动及 Apple 健康模式。成功保存后在本机按账号和服务地址记住所选方式和手动活动档。原始步数及训练时间在 iPhone 上计算，不上传。网页继续支持手动估算及记录校准。[HealthKit 日统计](https://developer.apple.com/videos/play/wwdc2020/10664/) · [计划与身体数据模型](../ios/SpotterHealth/NativeNutritionGoalModel.swift)
- 公式估算分四步。第一步，基础代谢用 Mifflin–St Jeor 公式。有体脂读数时，按每周训练天数向去脂体重公式 Cunningham（500 + 22 × 去脂体重 kg）过渡：每个训练日补上两者差值的五分之一，每周 5 天及以上完全采用。Cunningham 的结果不低于 Mifflin–St Jeor，也不超过它的 1.25 倍，所以体脂读数只会上调基础代谢。第二步，维持热量 = 基础代谢 × 活动系数。日常活动四档的系数为 1.5、1.6、1.7、1.9，每个训练日按 1 小时、3.5 MET 折入，系数增加 (3.5 − 日常系数) × 训练天数 ÷ 168。第三步，按目标调整：减脂的慢、标准、快为维持热量的 −10%、−20%、−25%，增重为 +5%、+10%、+15%。减脂每周不超过体重的 1%，每天最多少吃 1000 千卡；增重每周不超过 0.5%，每天最多多吃 500 千卡。BMI 不高于 18.5 时不提供减脂；高于它时，缺口还要保证按这个速度 8 周内不会降到 BMI 18.5 对应的体重，越接近越慢，界面注明。每周有训练且每天少吃超过 500 千卡时，提示这个幅度下很难再长肌肉；还有更慢的进度可选时，才建议放慢。体重变化按每公斤 7700 千卡换算，只作起步估计：界面写「约」，进度以称重为准。常规每周变化及每日增减上限在取整前计算。热量取整到 25 千卡，和维持热量相差不到 25 千卡时按维持显示，不写缺口或盈余。受 BMI 18.5 限制时只往维持热量一侧取整，取整后不会比这条限制更快；取整后和维持热量相同时，界面写「这次没有设缺口」。缺口不会让热量低于男性 1500、女性 1200 千卡，被上调时注明。维持热量本身低于这条线时不设缺口，照维持热量给出，也不再写放慢进度的说明。不论选哪个目标，给出的热量低于这条线时，都提示这个数低于一般的最低摄入量、建议先问医生或营养师。按记录校准出的维持热量同时低于这条线和公式值时不采用，改按公式并提示多半是饮食没记全；公式值本身就低于这条线的人，记录不低于公式值时照常采用。采用记录校准后，减脂的目标可能低于公式算的基础代谢：校准值最低是基础代谢的 1.2 倍，再减 25% 约为 0.9 倍，仍受最低热量限制。可估算的范围是年龄 18–120 岁、身高 100–250 cm、体重 10–700 kg，未满 18 岁不估算；Mifflin–St Jeor 算出非正数，或结果低于 800、高于 20000 千卡时也不给结果。第四步，蛋白质按每公斤体重 1.6 g（维持）、2.0 g（减脂增肌）、1.8 g（增重）、2.2 g（减脂），并保持在总热量的 10%–35%，被 35% 压低时界面注明。BMI 超过 25 时，参考体重取「BMI 25 对应的体重 + 超出部分的 25%」；有体脂读数时，再取它和「按 20% 体脂折算的体重（去脂体重 ÷ 0.8）」中较大的一个，且不超过实际体重，肌肉量大的人不会被 BMI 低估。脂肪取总热量的 25%，不低于每公斤 0.5 g，不高于 35%。其余热量给碳水，低于 130 g 时给出提示。
- 记录足够时，估算器在 iPhone 显示「采用近 4 周记录」，在网页显示「按近 4 周记录校准」。可信度为高或中时默认采用，为低时默认不采用，本人可以改。它用近 28 天的称重；饮食记录往前多读 9 天，共 37 天，用来分辨记录是早就在记还是刚开始。同一天多次称重取平均，偏离中位数超过 3 kg 且超过 4% 的读数视为输错。高于中位数 4 倍的饮食日视为输错，不计入。低于中位数一半或 600 千卡的日子算「记得特别少」：可能是没记全，也可能是真的吃得少，记录本身分不清。这样的日子不超过已记天数的 25% 时按一半计入，日均摄入取「只算完整日」和「全部已记日」两个均值的中点，另一半差值计入误差，界面注明有几天；超过 25% 时不给结果。饮食记录按中断分段：连续 5 天以上没有任何记录就断成两段，每次只用一段。优先用最近的一段；它给不出结果而更早的某一段可以时，用那一段；都给不出时显示最近一段的情况。体重趋势只用这一段里的称重，到这一段最后一个记录日的次日早晨为止，因为没记饮食时的体重变化说明不了记下的摄入。一段记录的第一天不在所读 37 天的头 3 天之内时，视为新开始或重新开始，它的头 7 天不计入：开始记录往往伴随改变饮食，身体水分大约一周才稳定。饮食只算所用首尾两次称重之间的日子，不含最后一次称重当天。至少需要 8 天称重、首尾相隔 14 天、其间 10 个完整饮食日且不少于这些天数的 60%，所以新开始记录的人大约 3 周后可用。推算值不是正数时也不给结果。实测维持热量 = 日均摄入 − 体重趋势斜率（最小二乘）× 7700。误差由五部分合成：体重趋势的误差（日波动不低于 0.3 kg，再乘 1.5 以计入连续几天的水分波动）、没记的日子带来的摄入抽样误差、每公斤能量的不确定度（减重 20%，增重 35%）、记得特别少的日子带来的那一半差值，以及换吃法带来的水分误差。最后一项这样判断：完整饮食日按日期分成前后两段，两段各不少于 4 天、均值相差 250 千卡以上且 t 值超过 3.5 时，认为期间换了吃法，误差加上 1 kg × 1.5 ÷ 天数 × 7700（28 天约 410 千卡），界面注明。这一项本身就超过 250 千卡，所以判断为换了吃法时可信度一定为低，默认不采用。采用值在实测值和公式值之间按精度加权，公式值的标准差取 15%。采用值限制在公式值的 ±25% 以内，且不低于基础代谢的 1.2 倍：触到下限时提示可能有漏记，触到上限时提示可能是日常活动选低了或体重变化里有水分。界面显示称重天数、每周变化、完整记录天数、日均摄入、实测值和 ± 误差，以及可信度（误差不超过 150 千卡为高，不超过 250 为中）。± 误差是上面五部分的合成，不含漏记，界面注明「未计漏记」。这个数字反映用户自己的记录口径，少记或漏记会让它偏低；只要记录习惯不变，按它定的目标仍对应预期的缺口。每公斤能量不按体脂调整：体脂低时实际值偏低，力量训练又让减掉的更多是脂肪，方向不定，已用 20% 的不确定度计入误差。已知局限，数字都来自模拟（每种情形 3000 个模拟用户，一直在记录的人），没有用真实用户的记录核对过。记录稳定时 98% 能给出结果，实测值没有系统偏差，真实值落在 ± 误差内的约占 70%。在这 4 周里开始节食（每天少吃 500 千卡、水分减少 1.2 kg）时实测值偏高约 240–510 千卡，结束节食时偏低约 180–460 千卡，变化发生在 2–3 周前时最大。换吃法的判断能认出其中 66%–84%，认出后默认不采用；勾选采用时，数值仍偏 120–270 千卡。这种情形下默认结果的平均误差约 200–265 千卡，和只用公式（约 215 千卡）相当，校准没有带来改善。饮食量平稳但前后几天相关，或在 4 周里慢慢漂移时，会被误判成换了吃法：逐日独立时约 2%，相关系数 0.2、0.4、0.6 时约 6%、14%、30%。误判的后果只是这次默认不采用。只在工作日记录而周末每天多吃 300–1000 千卡时，实测值偏低约 90–290 千卡，可信度仍多为高，误差不会反映。记录中断不到 5 天、其间每天多吃 800 千卡并带来 1 kg 水分时，实测值偏低约 220 千卡；中断期间吃得和平时一样时没有偏差。记得特别少的日子按一半计入，两种情况各错一半：每周真有一天只吃约 700 千卡的人，实测值偏高约 170 千卡；这些日子其实是没记全时，每有一天实测值偏低约 33 千卡。每周两天轻断食的人多数得不到结果。真正开始记录之前 4 天内零星记过一天时，那一天会并进同一段，实测值偏高约 110 千卡。新开始记录 3–5 周的人偏高约 50 千卡。水分波动连续多天时，每天称重的 ± 误差偏小。维持热量已包含训练消耗，界面提示同一次训练不用再通过「计入运动消耗」加到当天目标。

### AI 教练、导入与外部 Agent

- 站内 AI 使用当前账号的请求授权。在教练对话说「吃了一个蛋挞作加餐」这类已吃喝的本人餐食，App 或网页根据结构化估算自动记入对应日期和餐次，并显示可核对的保存回执。常见份量按合理大小估算并标明依据。紧接着说「帮我添加进去」时，已保存的餐食只回显，未保存的估算用同一笔记录重试。营养咨询、假设及他人餐食沿用问答。训练计划经预览确认后入日程。系统读取的 Apple 健康原始数据不随站内教练请求发送。
- 生成训练计划可用表单问答或对话，推荐可引用动作目录和官方模板。卡片按实际可用动作显示查看详情、加入训练或查看计划等操作。AI 用量在「设置 → AI 教练」，服务端按账号限制每 UTC 日 200、每 UTC 月 2,000 条消息，并另有月度费用预算。
- 「设置 → 外部 Agent」可创建和撤销个人连接，网页从「添加计划 → 用自己的 AI」进入。连接名称、有效期及可读写范围在创建时选择，权限默认全部勾选。新建页底部并排「全选授权」（全部选中时显示「取消全选」）和「创建连接」两个独立按钮，iPhone 固定在页面底部，网页放在对话框底栏。「复制提示词」提供一份通用文本，内含 MCP 和 OpenAPI 地址，以及编排训练、记饮食、分析记录、管理模板和演示动图的指令。连接创建后自动定位到提示词卡片，在同一卡片用「复制令牌」取得只在本次创建后提供的连接凭据。提示词粘贴到自己的 AI 对话框，令牌只填入外部工具的凭据设置。[原生连接](../ios/SpotterHealth/NativeAgentAccess.swift) · [网页连接](../cloudflare/features/agent-access/access-panel.tsx)
- App 的「设置 → 外部 Agent → 使用教学」和教练「用自己的 AI」的连接页共用四步教学。教程带用户选权限、配置自己的客户端、复制提示词执行示例，并在「我的连接」核对最近使用时间或撤销。新手引导高亮真实入口，使用教学只展示说明和示例。[SwiftUI 使用教学](../ios/SpotterHealth/NativeAgentAccess.swift)
- 外部 Agent 按当前账号的 `profileRef` 与连接权限校验归属。 复制提示词要求客户端先复用已授权连接，再在工具内部完成账号校验，成功后简短回复。上游 403 / Cloudflare 1010 依照 [Agent 接入指南](../cloudflare/docs/agent-api.md) 报告连接问题，连接凭据与权限标识不写入回复。权限区分编排资料、训练草稿、排期、分类读取和写入。健康原始读数、身体数据与搭子或好友的记录均在外部 Agent 读取范围之外。明确授权后才记餐，重试同一餐食复用原 UUID。[Agent 权限](../cloudflare/features/agent-access/model.ts)
- 外部 Agent 在生成或导入含动作的计划、周期和个人模板前，用 `read:context` 查当前账号的个人动作和内置目录。标准目录 ID 一致、明确登记为同一动作的别名或规范化后完全相同的名称可用于复用。相近变式各自保留。两端的复制提示词说明这个规则，iPhone 的使用教学同时提示开启「读取编排资料」。[编排资料接口](../cloudflare/features/agent-access/context.ts) · [网页提示词](../cloudflare/features/agent/guide.ts) · [原生提示词与教学](../ios/SpotterHealth/NativeAgentAccess.swift)
- 外部 Agent 管理个人模板时，用 `templates:read` 读取模板 ID 和版本，用 `templates:manage` 预览改名、替换整份动作列表或删除。预览展示对关联计划的影响，用户确认后提交同一个预览令牌。版本已变或预览到期时需重新核对。[模板修改服务](../cloudflare/features/agent-access/template-change.ts)
- 外部 Agent 收到附带演示的请求时，通过 `read:context` 查询同一动作，再调用 `get_spotter_exercise_demo_skill`。标准动作沿用目录 ID，已有的 Spotter 3D 示范可直接复用。新的个人动作可由 Agent 使用 [Spotter 动作渲染技能](../skills/spotter-exercise-demo/) 在本地生成并核对 GIF，再按现有确认流程保存。技能独立运行，只接收动作配方。选用一个相近动作时仍需保留其不同器械、握法和单侧等信息。[Agent 查询及写入规则](../cloudflare/docs/agent-api.md#用-spotter-技能生成动作示范)
- 所有新制作和更换的官方及个人动作素材默认采用 Spotter 原创 3D 样片。统一用连续蒙皮浅灰人体、深色运动装、浅灰背景、柔和地面阴影和局部肌肉高亮。渲染正确器械、握法与完整运动循环，封面使用成片实帧。该标准记录在 [AGENTS.md](../AGENTS.md) 和外部 Agent 指南，并出现在 [网页提示词](../cloudflare/features/agent/guide.ts)、[iPhone 提示词](../ios/SpotterHealth/NativeAgentAccess.swift)及技能下载包。
- 5,685 个标准动作全部按 [已核准的目录 ID](../cloudflare/features/exercises/spotter-demo-assets.json) 选择原创 3D 示范，iPhone 离线视频和 Cloudflare 网页使用同一对应关系。个人计划及其编辑页、训练过程和训练动作详情都可打开演示。旧计划只有名称时先匹配同一标准动作，同名歧义和个人变式保持独立。确认为同一个动作的别名写在 [目录精确别名](../cloudflare/features/exercises/catalogue-exact-aliases.json)，网页与 iPhone 共用。私有 GIF 只为当前账号的动作读取。扩充时用 [离线盘点工具](../tools/plan-exercise-demo-rollout.mjs) 依次整理个人计划、官方模板和整库。个人盘点报告留在本地，跨范围对同一目录 ID 去重，个人动作和同名歧义分别核对。
- [12 周功能性力量模板](../ios/SpotterHealth/Resources/official-training-templates.json)包含 12 周逐周安排，每周第 1、2、4、6 天训练，共 48 节。排期从使用者所选日期开始，按原组次和动作结构生成私有草稿，统一留空默认负重。已保存的重复周模板继续沿用原有格式。[模板模型和排期](../ios/SpotterHealth/NativeOfficialTemplateModel.swift) · [模板和筛选界面](../ios/SpotterHealth/NativeOfficialTemplates.swift)

- iPhone 动作详情的「历史」按训练列已完成组次，「统计」按日汇总训练容量和组数，并按有效组显示最大重量及设置中选择的 1RM 估算方法。两页只读本人记录，可加载更早的训练。动作匹配优先用准确目录 ID，个人动作和相近变式保持独立。「今日训练」的「动作演示」在开练前列出计划动作。进行中可从动作卡片的「动作演示」打开「要点」和示范，再切到「历史」或「统计」。对旧计划使用标准目录的旧 ID 映射或唯一精确名称。动作身份不一致时保留个人动作，未保存私人 GIF 时显示「此动作暂时没有演示动图」，读取失败可重试。变式使用目录已有分组、明确关联的个人变式，以及相同训练模式与主要肌群的参考动作。

- [演示审计](../cloudflare/scripts/audit-exercise-animations.mjs) 按目录实际选中的动画统计。`--list-illustrations` 列出仍为线条动画的标准动作，`--require-all-3d` 核对所有标准动作均使用同一目录 ID 的 3D 视频及封面。`--list-legacy` 和 `--require-original-replacements` 用于原有旧动图。按器械分组的 [配方源码](../tools/spotter-demo/) 覆盖自重、哑铃、绳索、杠铃、史密斯机、力量器械、弹力带、稳定球及有氧设备。核对关键帧后，用 [素材登记工具](../tools/spotter-demo/promote-reviewed-legacy.mjs) 的 `--illustrations` 模式核对具体 ID、视频和封面校验和，再生成 iPhone 离线资源。Mac 批量离线渲染可用 `SPOTTER_DEMO_SYSTEM_GPU=1` 调用系统 GPU。
- 线条演示重画以目录里该动作的关键帧和步骤为参考，保留单侧、握法、高度、动作顺序和器械支撑点。悬挂带根据固定扣点和带长追踪手脚位置，带有辅助者的练习使用两个人体。绳索握把、腕带、杠杆、滑轨、弹力带和辅助器材都随各自动作的接触点绘制。训练计划、模板、网页和 iPhone 离线包继续用同一目录编号加载。

## 变更与发布验证

1. 确认目标环境、账号和代码分支。设计有用户可见入口变化时，同时更新本文与 [产品帮助资料](../cloudflare/shared/product-help.json)。新增 API、权限或字段时更新对应业务文档、模型和运行手册。
2. 根目录运行 `npm test` 与 `npm run build`。Cloudflare 变更在 `cloudflare/` 分别执行 `npm test`、`npm run build`，有构建部署变化时跑 `npm run cf:dry-run`。
3. 原生改动运行 `npm run test:ios-app`、Xcode 模拟器构建，交互改动核对点击、恢复、无网情况、小屏和减少动态效果。Node 健康同步协议可运行 `npm run test:health-native`，模拟权限和数据使用合成账号。
4. 最终打包前获取需要的远端代码，执行 `npm run ios:source-check` 和 `npm run ios:package`，记录源码和 Cloudflare 后端版本。Xcode 归档后、上传 TestFlight 前运行 `npm run ios:verify-archive`，核对 Release 归档里的小组件扩展、灵动岛界面、`NSSupportsLiveActivities` 和 Watch App。使用 [App 构建说明](iphone-app.md#构建) 和 [Cloudflare 部署说明](../cloudflare/README.md#cloudflare-部署) 核对适用配置。
5. 真机验收单独记录 iPhone、Apple Watch、系统授权、后台补传、APNs、登录绑定和开发/分发签名的实际状态。合成测试只填写合成结果，按目标环境验证供应商 OAuth 与已部署 API。
